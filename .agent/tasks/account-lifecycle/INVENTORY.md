## Current deletion

- **Self-service (`DELETE /profile`):** [ProfileController.php](app/Http/Controllers/ProfileController.php#L60-L75) validates `current_password`, calls `UserAuthorization::delete($user, $user, selfService: true)` (`:68`), then logs out and invalidates/regenerates the caller's session (`:69-72`).
- **Admin (`DELETE /admin/users/{user}`):** [Admin/UserController.php](app/Http/Controllers/Admin/UserController.php#L99-L113) calls `UserAuthorization::delete($request->user(), $user)` (`:102`) and only logs out/invalidates the current HTTP session if deleting self (`:101,104-108`).
- **Core delete (`UserAuthorization::delete`):** [UserAuthorization.php](app/Authorization/UserAuthorization.php#L74-L118):
  1. Authorizes self-service (`:76-77`) or `manage-user-account` gate (`:79`).
  2. If target is `super_admin`, atomically pulls `_id` from `authorization_control/super-admins.user_ids` only when ≥ 2 members remain (`:84-86`, [SuperAdminGuard.php](app/Authorization/SuperAdminGuard.php#L38-L44)).
  3. If target `isAdmin()`, builds an `account_deleted` audit event (`:83`) and calls `ApiTokenService::revokeAllForUser()` (`:90-101`) wrapping a Mongo `updateOne` that demotes `role`→`user`, clears `permissions`, sets `authorization_deleting`/`authorization_deleting_at`, increments `api_token_epoch`, and pushes the event into `users.authorization_audit_pending`.
  4. Copies `users.authorization_audit_pending` to the standalone `authorization_audit_pending` collection (`:105`, [AuthorizationAudit.php](app/Authorization/AuthorizationAudit.php#L125-L131)).
  5. **Hard-deletes** the Mongo `users` document immediately via raw `deleteOne($filter)` (`:106-108`) — no soft-delete, no 30-day recovery window, and Eloquent `User::deleted` ([User.php](app/Models/User.php#L35)) does not fire.
  6. Best-effort clears Redis API token families via `ApiTokenService::cleanupForUser()` (`:114`) and attempts immediate Cassandra delivery of the staff audit event (`:115-117`).

## Stripe

- **No programmatic cancellation exists anywhere in `app/Billing/*` today.** [StripeClient.php](app/Billing/StripeClient.php#L5-L16) and [StripeSdkClient.php](app/Billing/StripeSdkClient.php#L7-L45) expose only `createCustomer`, `updateCustomer`, `createCheckout`, `createPortal`, and `retrieveSubscription` (`max_network_retries => 1`).
- Today, subscriptions are only canceled manually by users inside Stripe Billing Portal ([BillingController.php:45-57](app/Http/Controllers/BillingController.php#L45-L57) → [BillingGateway.php:61-66](app/Billing/BillingGateway.php#L61-L66)).
- Webhook projection ([BillingGateway.php:187-298](app/Billing/BillingGateway.php#L187-L298)) handles `checkout.session.completed` and `customer.subscription.{created,updated,deleted}` by re-fetching the subscription from Stripe (`:240`), falling back to `status => 'canceled'` only on `SubscriptionMissing` for `.deleted` (`:241-247`), and projecting `status`, `cancel_at_period_end`, `canceled_at`, `cancel_at`, `ends_at` (`:280-282`).
- **Critical webhook behavior for deletion:** At [BillingGateway.php:256-265](app/Billing/BillingGateway.php#L256-L265), if `User::find($userId)` and `User::where('stripe_customer_id', $customer)->first()` both miss, `apply()` logs `Billing webhook user not found`, leaves any already-projected `subscriptions` document untouched, and returns `'unknown_user'`. If deletion hard-deletes or hides soft-deleted users from `User::find()`, Stripe cancellation webhooks won't update local `subscriptions`.
- For account deletion, `StripeClient`/`BillingGateway` will need a new idempotent `cancelSubscription` (and/or customer active-subscription list + cancel) method with deterministic idempotency key (e.g. `vietfeed-delete-cancel-<sub_id>`).

## Orphans today

Because `UserAuthorization::delete()` only deletes Mongo `users` (plus `SuperAdminGuard` + Redis API token families), deleting a user today orphans:
1. **Stripe:** active `Subscription` continues billing; `Customer` retains email/name/metadata.
2. **MongoDB:** `subscriptions` (still `status: active` — `BillingGateway::proUserIds()` still returns the deleted ID), `comments` (live comments + replies with dangling `user_id`), `bookmarks`, `boosts`, `article_unlocks`, `authorization_control.bootstrap_user_id` (if the bootstrapped Super Admin is deleted).
3. **Redis:** `interactions:trending:v1` retains +5 boost points for orphaned boosts; `reading-pass:v1:u:<id>:w` stays until 26h TTL; password reset token stays until 60m TTL; other browsers' web sessions (and target's session on admin delete) remain in Redis until 120m TTL (currently neutralized only because `users` doc is gone); unconsumed/DLQ stream messages in `interactions:*` and `reading-pass:*`.
4. **Cassandra:** `activity_by_user_month`, `activity_by_article_day` (`user_id`), `unlocks_by_user_month` (no TTL).
5. **Intentionally retained (not bugs, but dangling `user_id` refs):** `reports`, `moderation_cases`, `sanctions`, `story_briefs.reviewed_by`, `authorization_audit_pending`, Cassandra `authorization_audit_by_*` and `moderation_events_by_case`.

## Risks

1. **Web sessions stay alive during 30-day soft-delete:** Unlike hard-delete, keeping a soft-deleted `users` doc lets existing Redis sessions and `remember_token` cookies keep authenticating unless `Auth`/middleware rejects pending-deletion users and `remember_token` is cleared immediately (Redis sessions have no `user_id` index).
2. **Unique Mongo indexes block re-registration during 30-day recovery (or break recovery):** `users` has unique indexes on `email`, `google_id` ([GoogleAuthController.php:46-48](app/Http/Controllers/Auth/GoogleAuthController.php#L46-L48)), and partial unique `stripe_customer_id` ([2026_11_17_000001_create_mongodb_billing_indexes.php:26](database/migrations/2026_11_17_000001_create_mongodb_billing_indexes.php#L26)). Decide explicitly whether `email`/`google_id` stay reserved for 30 days (preventing hijack before recovery) and guard `GoogleAuthController::callback()` (`:49-53`) and `PasswordResetLinkController` so OAuth/reset cannot silently log into or overwrite a pending-deletion account.
3. **Comment cascade deletes other users' replies:** Calling `$comment->delete()` triggers `Comment::booted()` ([Comment.php:34-39](app/Models/Comment.php#L34-L39)), recursively deleting replies authored by other users. Purge must anonymize comments in place rather than deleting parent comments.
4. **Cassandra partition discovery & non-atomic cross-store purge:** `activity_by_user_month` and `unlocks_by_user_month` are partitioned by `(user_id, year_month)` with no index of active months; purge must iterate UTC months from `user.created_at` to `purge_at` (and read `activity_by_user_month` to locate exact `activity_by_article_day` PKs **before** deleting `activity_by_user_month`). Store workflow state/checkpoints in Mongo (`account_deletion_workflows` per [database-feature-map.md:73](docs/architecture/database-feature-map.md#L73)) so retries are idempotent if Cassandra/Neo4j/Stripe is down.
5. **Late stream events recreating Cassandra rows after purge:** Unconsumed/DLQ events in `interactions:events:v1` or `reading-pass:events:v1` (or `reemit` commands) could re-insert Cassandra rows if consumers run after purge without checking deleted/workflow state or draining first.
6. **Stripe outages & webhook races:** Canceling Stripe synchronously in the HTTP delete request can fail if Stripe is down; `BillingGateway::apply()` (`:257-265`) must still recognize a pending-deletion user (or update `subscriptions` by `_id`) so `customer.subscription.deleted` webhooks reconcile cleanly.
7. **Banned user self-deletion vs. sanctions policy:** `CheckUserSanction` ([CheckUserSanction.php:23-29](app/Http/Middleware/CheckUserSanction.php#L23-L29)) blocks permanently banned users from `/profile` (`DELETE /profile`), while temp-banned users can still reach it; confirm whether banned users may delete/recover and ensure sanctions/appeals stay intact and cannot be bypassed via delete+re-register.
8. **Super Admin guard during 30-day recovery:** Decide whether `SuperAdminGuard::reserveRemoval()` runs at deletion request (blocking recovery as Super Admin) or if Super Admins must be demoted before self-deletion.
